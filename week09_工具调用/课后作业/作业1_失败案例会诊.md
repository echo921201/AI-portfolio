# 作业 1：失败案例会诊 —— 复合问句答一半

## 一、现象

问句：**「请依次查询两件事：1. '把'字的 HSK 等级是多少？2. 现在的时间是多少？」**

课堂上连跑 5 次，只有 2 次把 `hsk_level` 和 `get_time` 都调了；另外 3 次只调了 `hsk_level`，答完第一个子问题就收手了。失败时是这样：

```text
[第1轮] 模型原始输出：{"tool": "hsk_level", "args": ["把"]}
[第1轮] 解析到的调用：[{'tool': 'hsk_level', 'args': ['把']}]
[第1轮] 工具返回：hsk_level['把'] → 把 是 3 级
[第2轮] 模型原始输出：“把”字的 HSK 等级是 **3 级**。
[第2轮] 解析到的调用：[]          ← 这一轮没有点名 get_time，循环收口
```

用户问了两件事，只答了一件——问的明明是「现在几点」，返回里却连时间两个字都没有。

## 二、原因分析

把三段证据摆在一起看：

1. **`SYS` 里写的是「一次只调用一个工具」**。模型严格遵守了这句话，一轮只点名一个工具。
2. **一轮结束后结果被回喂**，模型看到「工具返回：把 是 3 级」，判断「问题已经答完了」，第二轮直接生成自然语言。
3. 于是第二个子问题永远没有机会被处理——**不是工具坏了，是循环提前收口了**。

这里有个容易搞错的地方：不是模型「笨」，是**提示词和循环设计一起把路堵死了**。`SYS` 说一次调一个，`max_calls=2` 又只给两轮，第二轮一旦用来生成答案，就再也没有下一轮去补第二个工具。

## 三、约束改法（三条，由易到难）

| # | 改法 | 说明 |
|---|---|---|
| 1 | 问句写成编号列表 | 课堂用的就是这种（1. … 2. …），比口语式问句「'把'字几级？现在几点？」成功率高 |
| 2 | `SYS` 末尾加一句「问句里有几个子问题，就依次调用几次工具，全部查完再作答」 | 把「一轮一个工具、但要把子问题补齐」的意图写死 |
| 3 | `max_calls` 从 2 提到 3 | 成功的那几次正是第 2 轮才点名 `get_time`；上限 2 时如果第一轮就被当成最终答案，没有第二次机会 |

## 四、对比实验（改法 2，实测）

只改 `SYS` 一句话，别的都不动，同一个问句各跑 5 次：

```
[A] 原版 SYS（一次只调用一个工具）：两个工具都调 3/5
      get_time+hsk_level / hsk_level / get_time+hsk_level / hsk_level / get_time+hsk_level

[B] SYS 末尾加「有几个子问题就调用几次工具」：两个工具都调 5/5
      get_time+hsk_level × 5
```

**3/5 → 5/5**，而且改法 2 不需要动任何代码逻辑（`parse_calls`、`run`、工具函数全没碰），只是把意图说清楚。

实验脚本：`week09_工具调用/课后作业/exp_sys_compare.py`（它不改 `tool_agent.py`，只在运行前替换 `SYS` 并包一层 `TOOLS` 记录调用情况）。

## 五、结论

- 工具调用的稳定性**不只取决于模型**，提示词里「一次一个」和「把子问题补齐」是两件事，必须分开说清楚。
- 改提示词比改代码便宜：`max_calls` 涉及收口条件，动它要重新想清楚「什么时候停」；`SYS` 加一句话风险为零。
- 这也解释了为什么讲义要求「把失败时的原始输出、解析结果、工具返回值三段都留在轨迹记录里」——没有这三段，只能猜；有了这三段，原因一眼就能定位到「第 2 轮没点名工具」。
