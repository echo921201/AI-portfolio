# M1 会话协议草案

> 目标：把「用户说话 → 助手思考 → 调工具 → 说话」这一串，定成一套客户端与服务端都认的事件流。
> 一句话原则：**服务端唯一权威，客户端只是渲染器；一切以 `seq` 为准。**

## ① 事件类型与字段

所有事件都是同一个信封，`type` 区分语义：

```json
{ "session_id": "s-8f3a…", "seq": 42, "ts": 1763900000123, "type": "agent.speech.delta", "payload": { … } }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | string | 一次会话唯一，重连后不变（变了就是新会话） |
| `seq` | int | 会话内**严格递增**，从 1 开始，不跳号 |
| `ts` | int | 毫秒时间戳，仅用于展示与排障，**不参与排序** |
| `type` | string | 事件类型（见下表） |
| `payload` | object | 该类型自己的数据 |

| type | 方向 | payload 关键字段 |
|---|---|---|
| `session.ready` | S→C | `server_version`、`resume_from` |
| `user.speech.partial` | C→S | `text`（ASR 中间结果，可覆盖） |
| `user.speech.final` | C→S | `text`、`audio_ms` |
| `agent.thinking` | S→C | `note`（可空，用于显示“思考中”） |
| `tool.call` | S→C | `call_id`、`tool`、`args` |
| `tool.result` | S→C | `call_id`、`ok`、`result` / `error` |
| `agent.speech.start` | S→C | `utterance_id` |
| `agent.speech.delta` | S→C | `utterance_id`、`text_delta` |
| `agent.speech.end` | S→C | `utterance_id`、`full_text` |
| `interrupt` | C→S | `utterance_id`、`reason` |
| `error` | S→C | `code`、`message`、`retryable` |

**约定**：`tool.call` 与 `tool.result` 用 `call_id` 配对；`agent.speech.*` 用 `utterance_id` 配对。**不靠顺序猜配对**——顺序会因补发、并发而不可靠。

## ② 状态机

```
                 user.speech.final
   ┌────────┐  ───────────────────▶ ┌───────────┐
   │  idle  │                        │ listening │
   └────────┘ ◀───────────────────  └───────────┘
       ▲            session.end            │ user.speech.final
       │                                   ▼
       │                            ┌───────────┐
       │        error（任意态）       │ thinking  │
       │  ◀──────────────────────   └───────────┘
       │                              │        ▲
       │                    tool.call │        │ tool.result
       │                              ▼        │
       │                        ┌──────────────┴──┐
       │                        │  tool_calling   │
       │                        └─────────────────┘
       │                              │ 工具全部返回
       │                              ▼
       │                        ┌───────────┐
       └────────────────────────│ speaking  │
              speech.end        └───────────┘
```

- **打断回退**：`speaking` 收到 `interrupt` → 立刻转 `listening`，丢弃该 `utterance_id` 后续的 `delta`。已经在跑的 `tool_calling` **不取消**（工具可能有副作用），但结果不再播报。
- **错误恢复**：任意态收到 `error` 且 `retryable=true` → 回 `idle`，等客户端重发；`retryable=false` → 进 `failed`，只能 `session.end`。
- **不允许多态并存**：一个会话在任一时刻只有一个状态，服务端是唯一的状态持有者。

## ③ 权威与幂等

- **服务端唯一权威**：客户端**不得**自行拼接最终答案或猜测工具结果，只按事件渲染。
- **按 seq 去重**：客户端记录 `last_seq`，收到 `seq <= last_seq` 的事件直接丢弃。这样补发、重复投递都不会让界面“说两遍”。
- **工具调用幂等**：`tool.call` 带 `call_id`（服务端生成）。客户端重发同一 `call_id` 时，服务端返回缓存结果，不重复执行——写文件、发消息这类副作用工具尤其需要。
- **冲突优先级**：用户的 `interrupt` 高于正在播报的 `speech.delta`；先到者生效，后到的 `delta` 直接丢。

## ④ 断线语义

- 客户端断线时**保留 `last_seq`**（内存或本地存储，按 `session_id` 存）。
- 重连发 `session.resume { session_id, last_seq }`：
  - 服务端从 `last_seq + 1` 起**按序补发**，补完再转实时；
  - 超过保留窗口（例如只保留最近 1000 条）→ 不补发，直接回 `session.snapshot { full_state }`，客户端整体重置。
- **服务端不因客户端断线而中断任务**：思考和工具调用继续跑，事件照常入队，就等它回来补发。
- 客户端连续重连失败超过阈值 → 显示“连接已断开”，**不要**自己伪造结束状态。

---

## 一页总结

| 问题 | 答案 |
|---|---|
| 谁说了算 | 服务端；客户端只渲染 |
| 怎么去重 | 按 `seq`，`last_seq` 之前的丢弃 |
| 怎么配对 | `call_id` / `utterance_id`，不靠顺序 |
| 断线怎么办 | 带 `last_seq` 重连，服务端补发或给全量快照 |
| 打断怎么办 | 停播报、回 `listening`，但已发起的工具调用不取消 |
